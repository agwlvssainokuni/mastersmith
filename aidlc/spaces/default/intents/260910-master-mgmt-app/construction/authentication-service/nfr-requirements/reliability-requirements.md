# Reliability Requirements — authentication-service (U5)

## NFR4.1: 更新の原子性と競合の扱い

要件のNFR4は、同時更新の競合を検出することを求める。本ユニットは、業務データの楽観ロック(要件のFR6.3)の対象ではなく、次の更新を、条件付きの原子的な更新で行うことで、この要件を満たす。

- **ログインの試行の枠の確保(予約)**: `AccountLoginState`に対する1つの原子的な更新(なければ作成する場合を含む)で、しきい値に達する更新と同時に`lockedUntil`を設定する(rules.md BR5.3)。同時の試行が何件あっても、1回のロック期間に検証できる試行は、しきい値の回数を超えない。
- **補償の更新**(ハッシュ計算の上限超過の503で枠を返す): 予約の時点と`generation`が同じで、`consecutiveFailures`が0より大きい場合に限る。ロックは、この予約が設定した`lockedUntil`と一致する場合に限り解く。条件を満たさなければ何もしない(回数が負にならず、新しい世代の失敗を数え損ねない、BR5.3)。
- **ログインの成功**: `AccountLoginState`のリセット(回数を0、`lockedUntil`を空、`generation`を1増やす)と、Sessionの作成を、**同一の短いトランザクション**で行う([assumption]。機能設計のW1は、この2つを順に記述している。分けると、リセットだけが反映されて、Sessionの作成が失敗した場合に、利用者に成功が返らないのに、回数だけが0に戻る、という中途半端な状態が残りうる。同一のトランザクションなら、両方が反映されるか、どちらも反映されない)。
- **リフレッシュ**: `previousRefreshTokenHash`の移行と、`refreshTokenHash`・`lastRefreshedAt`・`refreshExpiresAt`・`activeRoleId`の更新を、1つの条件付きの更新で行い、同一のリフレッシュトークンの同時の更新では、1件だけが成功する。更新の件数が0件だった側は、401を返し、Sessionは失効させない(BR5.6)。
- **失効の更新**(ログアウト・盗用の疑い・ユーザーの無効化の検知): Sessionをrevokedにする更新は、冪等とする。すでにrevokedであっても、エラーにしない。
- **ハッシュ計算の間の資源**: C11の各メソッドは、トランザクションの外で呼ぶ(BR5.15)。予約の更新・成功の更新・補償の更新は、それぞれ短いトランザクションとし、C11の呼び出しの間に、内部設定DBの接続を保持しない。
- 要件のNFR4の、もう1つの内容である「監査ログの改ざん・削除不可(FR8.2)」は、本ユニットが監査ログを発行しない(機能設計のAssumptions)ため、対象外である。

## NFR4.2: 内部設定DBの障害時の応答

Q5=Aにより、内部設定DBが一時的に使えないとき(接続の取得の待機の超過・ロックの待機の超過・DBの停止など)は、**503**(一時的に処理できない、RFC 9457のProblemDetails)を返し、401にはしない。

- 対象: 認証フィルタ(キャッシュミスで、Sessionを内部設定DBから引けないとき)・ログイン・リフレッシュ・ログアウト・ロール選択のすべて。認証を必要とするすべてのAPI(他のユニットのAPIを含む)が、認証フィルタで、この503を受ける。
- **fail closed**: Sessionを確認できないまま、リクエストを通すことはしない(500にもしない)。
- キャッシュに、有効なSessionがある場合は、内部設定DBの障害の間も、認証フィルタは、キャッシュの内容で判定する([assumption]。キャッシュは、失効・ロールの選択のたびに無効化される(NFR4.3)ため、DBの障害が、認証の判定を古くすることはない。ただし、後続の処理がDBを必要とするなら、そちらが失敗する)。
- リフレッシュで、DBの障害のために更新が完了しなかった場合は、リフレッシュトークンを更新しない(ローテーションしない)。クライアントは、同じトークンで、再試行できる。
- 503の応答は、原因(接続の枯渇・タイムアウトなど)の詳細を含めない(NFR2.8)。件数は、NFR5.1の`auth_db_unavailable_total`で記録する。
- C4の全エンドポイントと、認証フィルタの契約への、503の追補を要する。ログインの503(ハッシュ計算の上限超過)は、機能設計のBR5.15で追補済みである。追補一覧(tech-stack-decisions.md)に記録する。
- frontend-ui(U12)は、503を、認証の失敗と区別して扱う(NFR2.11)。

## NFR4.3: Sessionのキャッシュの整合性

- ログアウト・無効になったトークンの再使用の検知・リフレッシュ時のユーザーの無効化の検知によるSessionの失効、アクティブロールの選択、リフレッシュ時のアクティブロールの再確認による変更は、**同じプロセス内では、次のリクエストから直ちに反映される**こと(キャッシュは、これらの更新のたびに無効化する。BR5.11、機能設計W4)。キャッシュの古さを許容する期間は、ゼロとする。
- キャッシュの更新の順序: 内部設定DBの更新に成功してから、キャッシュを無効化する。DBの更新に失敗した場合は、キャッシュを変更しない。
- 複数プロセス構成でのキャッシュの整合は、NFR3.5のとおり、全体設計に委ねる。

## NFR4.4: 起動時の設定検証(fail fast)

設定定義自体の誤りは、起動時に検知してfail fastする(project.md Mandated、rules.md BR5.4・BR5.5)。次のいずれかの場合に、起動を失敗させる。エラーのメッセージには、鍵などの値そのものを含めない(NFR2.7)。設定のキーの名称は、Code Generationで確定する。

| 設定 | 既定値 | 起動を失敗させる条件 |
|---|---|---|
| JWTの署名の鍵 | なし(環境変数などから注入) | 未設定、または256ビット未満(NFR2.2) |
| アクセストークンの有効期限 | 10分 | 0以下 |
| リフレッシュトークンの有効期限 | 30分 | 0以下、またはアクセストークンの有効期限より短い |
| リフレッシュの再送の猶予 | 10秒 | 負の値(0は許す。0にすると、猶予なしで再使用の検知を行う) |
| ロックのしきい値 | 5回 | 0以下 |
| ロック時間 | 15分 | 0以下 |
| Sessionの削除の保持日数(NFR4.5) | 7日 | 負の値 |
| Sessionの削除の実行間隔(NFR4.5) | 1日 | 0以下 |

上の表のうち、Sessionの削除に関する2つの設定は、Q4=Aで確定した設定であり、それ以外は、機能設計のBR5.4・BR5.5で確定している。値の関係(アクセストークンの有効期限が、リフレッシュトークンの有効期限を超えない)は、機能設計のBR5.4に従う。

## NFR4.5: 期限切れ・失効したSessionの定期削除

Q4=Aにより、期限切れ・失効したSessionを、バックグラウンド処理で削除する。

- 実行: **1日1回**(`application.yml`で変更できる)。Springの標準の定期実行の仕組みを用いる(追加のミドルウェアは導入しない)。
- 削除の対象: `refreshExpiresAt`が、**現在時刻から保持日数(既定7日)より前**のSession。失効(revoked)したSessionも、同じ基準で削除する([assumption]。Sessionには、失効の日時の専用の属性がない。専用の属性を増やすと、機能設計のエンティティの変更になるため、採用しない)。この基準では、有効期限より前に失効したSessionは、失効から7日以上たって削除される。有効期限のあとに失効した場合(猶予を超えた古いトークンの再使用の検知、BR5.6)は、失効から7日未満で削除されることがある。どちらも、直近のログインの状況を調べる用途には、支障がないと判断する。
- 有効なSession(statusがactiveで、`refreshExpiresAt`が未経過)は、削除しない。削除の条件に、`refreshExpiresAt`の比較を含め、Sessionのstatusだけで判定しない。
- 大量の削除で、内部設定DBのロックを長く保持しないよう、1回のトランザクションで削除する行数に上限を設け(たとえば1,000行)、残りは、続けて次のトランザクションで削除する([assumption]。上限の値は、NFR Designで確定する)。
- 削除に失敗しても、認証には影響させない。失敗は、エラーとして構造化ログに記録し(NFR5.2)、次の実行で再試行する。
- 削除の処理は、認証のリクエストの処理(ログイン・リフレッシュ・認証フィルタ)と、同じ行を書き換えないため、競合しない(削除の対象は、すでに有効でないSessionだけである)。

## NFR4.6: 時刻の扱い

- ロックの解除の判定・Sessionの有効期限・アクセストークンの有効期限は、いずれも、アプリケーションが動作するサーバーの時計を、時刻の唯一の供給元とする([assumption])。テストでは、時計を差し替えられるようにする(有効期限・ロック・猶予の境界の自動テストのため)。
- サーバーの時計は、運用環境で、時刻の同期(NTPなど)が取られていることを前提とする。時計が大きく戻ると、ロックの解除が、その分だけ遅れ、期限を過ぎたトークンやSessionが、その分だけ長く受け入れられる。この影響を避けるため、時刻の同期は、環境の前提として記録しておく([assumption]。運用フェーズが本MVPスコープ外のため)。

## NFR4.7: 永続性・再起動・復元

- Sessionと`AccountLoginState`は、内部設定DBに永続化される。アプリケーションの再起動後も、有効なSessionは、リフレッシュトークンの有効期限まで有効である。ただし、内部設定DBが、再起動で内容が失われる構成(たとえば、メモリのみの組込みDB)の場合は、すべてのSessionが失われ、利用者は再ログインになる。この場合も、認証の安全性は損なわれない(失われたSessionは、有効でないものとして扱われる)。
- JWTの署名の鍵は、再起動をまたいで同じ値を注入する(NFR2.2)。鍵が変わると、発行済みのアクセストークンが1回使えなくなるだけで、リフレッシュで復旧する。
- Sessionのキャッシュは、再起動で空になり、最初のリクエストごとに、内部設定DBから読み込まれる(キャッシュミスとして扱われる)。
- 内部設定DBを、過去の時点のバックアップから復元した場合、復元の時点より後に失効した(ログアウトされた・盗用の疑いで失効した)Sessionが、activeに戻る。復元のあとは、Sessionをすべて削除する(または鍵を差し替えたうえでSessionを削除する)ことを、運用の手順の前提として記録しておく([assumption]。運用フェーズが本MVPスコープ外のため、担当が定まるまでは、環境側の前提として記録する)。

## NFR4.8: 可用性・バックアップ

authentication-serviceは、アプリケーション本体(単一WAR)の可用性に従属する。ユニット単体の独立した可用性目標(SLA/SLO)は設定せず、アプリケーション全体の目標に含める(運用フェーズが本MVPスコープ外のため、具体的な数値目標は設定しない)。認証が使えなくなると、認証を必要とするすべてのAPIが使えなくなる点は、他のユニットと異なる特徴として記録する。Session・AccountLoginStateは内部設定DB(組込みDB)に保持され、バックアップ・リカバリ方針は内部設定DB全体(他ユニットと共通)のものに従う(NFR4.7の復元時の注意を除き、本ユニット固有の追加要件はない)。

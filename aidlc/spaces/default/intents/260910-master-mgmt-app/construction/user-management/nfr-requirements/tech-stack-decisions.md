# Tech Stack Decisions — user-management (U4)

基本の技術スタックはFeasibilityステージ(2026-09-10)・practices-discoveryで確定済み(`team.md`参照)であり、本ユニット固有の選定は次の表のとおりである。

| 領域 | 選択 | 根拠 |
|---|---|---|
| 言語・フレームワーク・ビルド | Java 25 + Spring Boot + Gradle | プロジェクト全体で確定済み |
| パスワードハッシュ | Argon2id。実装はSpring Securityの`Argon2PasswordEncoder`。内部で使われるBouncyCastle(`org.bouncycastle:bcprov-jdk18on`)を依存に追加する | Q6=A。Spring Bootとの統合が容易で、ログインを担当するauthentication-serviceと同じ仕組みを共有しやすい。バージョンは実装時に最新の安定版を確認する |
| 同時ハッシュ計算数の制御 | JDK標準の同時実行制御(セマフォ等)。上限の既定はCPUコア数、待機上限2秒 | NFR1.3(Q2=A・Q2 Follow-up)。具体的な実装方式はCode Generationで確定する |
| メール送信 | SMTP経由。Spring Bootのメール送信機能(`spring-boot-starter-mail`)を想定。開発・動作確認用にMailpitを用意する | FR2.8。ライブラリの最終確認はCode Generationで行う([assumption]) |
| メールテンプレート | **自作のmustacheエンジン**(ユーザー指示)。Gitサブモジュール等で別リポジトリのソースをビルド時に取り込む | Q7=C。取り込みの詳細は下記「確認事項」 |
| メールの形式 | **HTMLメール**。件名(Subject)は、レンダリング後のHTMLの`<title>`要素の値から抽出する | ユーザー指示。NFR2.7も参照 |
| データストア | 内部設定DB(組込みDB、例: H2)、業務データ用RDBMSとは別接続 | Userはアプリ自身のユーザー情報であり業務データではないため、他ユニットと同じく内部設定DBに置く(team.md Q12b) |
| メトリクス・トレーシング | NFR5.1・NFR5.3に従いOTEL基盤へエクスポート(具体的なライブラリ選定はCI Pipelineで確定) | プロジェクト全体の可観測性方針に従う |

## 確認事項(Code Generationの計画承認までに確認する)

自作mustacheエンジンと、HTMLメールの作り方について、実装前に次を確認する。いずれも本ステージでは確定しておらず、Code Generationの計画承認までに、ユーザーへ確認する。

1. **取り込み方**: Gitサブモジュール等の取り込み先(リポジトリのURL・ブランチ・コミット固定の方法)、このプロジェクトのGradleビルドからどう参照するか(別ビルドとして取り込むか、ソースとして組み込むか)。
2. **mustache構文の範囲**: 使う機能(変数、セクション、反転セクション、部分テンプレートなど)と、エスケープの仕様(既定でHTMLエスケープされるか、エスケープなしの展開の書き方)。
3. **ライセンス上の注意**: 自作エンジンとこのプロジェクト(Apache License 2.0)の関係。
4. **件名の抽出方法**: `<title>`要素の値をどう取り出すか(HTMLパーサを使うか、単純な文字列処理か)。`<title>`の値にもテンプレートの変数を含められるか(レンダリング後に抽出する前提)。なお、抽出した値の文字参照のデコード、改行の拒否、最大長(200文字)の扱いは、security-requirements.md NFR2.7で定めた。
5. **テンプレートに`<title>`が無い、または空の場合**: テンプレートは設定定義にあたるため、起動時にfail fastして検知する方針を想定する([assumption]。project.md Mandatedの「設定定義自体の誤りはfail fastする」に準じる)。
6. **テキスト版(プレーンテキスト)の要否**: HTMLをうまく表示できないメールソフト向けに、テキスト版をあわせて送る(multipart/alternative)か、HTMLのみとするか。ユーザー指示は「HTMLメール」であり、テキスト版の要否は未確認。
7. **テンプレートの置き場所と、言語ごとの切り替え**: 言語(ja/en)ごとのテンプレートファイルの配置(NFR7.1)。
8. **リバースプロキシのログ(環境側の前提)**: リバースプロキシ等を使う環境では、招待トークンのURLパスをマスクする設定が必要になる(security-requirements.md NFR2.10)。運用フェーズが本MVPスコープ外のため、担当が定まるまでは、環境側の前提として記録しておく。

## 決定: 追加ミドルウェアを導入しない

メール送信は、既存のSMTPサーバー(開発ではMailpit)へ同期的に行う(NFR1.4)。メールキュー等の追加ミドルウェアは、本MVPスコープでは導入しない(非同期送信案は、Q3で不採用)。

## NFR7.1: 招待メールの言語(i18n)

Q8=Aにより、招待の操作(`POST /api/users`)に任意項目として言語(ja/en、省略時はja)を追加し、管理者が招待メールの言語を選ぶ。テンプレートは言語ごとに用意する。

- この追加は、招待APIの契約(C5)への追補と、機能設計(functional-spec.md W1、rules.md BR4.1)への反映を必要とする。機能設計は完了済みのため、追補としてCode Generationの計画承認までに反映する(作業メモにも記録する)。
- 再招待(rules.md BR4.11)でも、その時点で指定された言語でメールを再送する。

## NFR7.2: バリデーションエラーメッセージのi18n

要件のFR10.1(表示名・バリデーションメッセージをi18nキーで多言語対応可能な構造にする)に従い、user-managementのAPIが返すフィールド単位のバリデーションエラー(422のProblemDetailsの`errors[].message`。rules.md BR4.2・BR4.5・BR4.15など)は、**i18nキー**で表す。文言への変換(翻訳)は、フロントエンド(frontend-ui, U12)が、config-engineが管理する翻訳リソースを用いて行う([assumption]。要件はi18nキーで多言語対応可能な構造とすることのみを定めており、サーバーが翻訳するかフロントエンドが翻訳するかは定めていない)。

- キーの命名と、メッセージにパラメータ(文字数の上限など)を持たせる方法は、契約追補(保留)として、下記の一覧に記録する。
- サーバーの応答には、パスワードなどの入力値そのものを含めない(security-requirements.md NFR2.2)。

## 契約追補(保留事項の一覧)

本ステージ(NFR Requirements)で判明した、契約(C5・C11)・機能設計への追補のうち、確定していないものを一覧にする。機能設計・契約設計は完了済みのため、いずれも、Code Generationの計画承認までに反映する保留の追補として扱う(機能設計の見直しか、追補で済ませるかは、その時点で判断する)。

| 番号 | 対象 | 内容 | 出典 |
|---|---|---|---|
| 1 | C5 招待API(`POST /api/users`) | 任意項目`locale`(ja/en、省略時ja)の追加。機能設計のW1・BR4.1にも反映が必要 | Q8=A、NFR7.1 |
| 2 | C5 招待受諾API | ハッシュ計算の待機超過を表す503レスポンスの追加 | NFR1.3 |
| 3 | C11 UserAccountLookupApi | ハッシュ計算の待機超過を表す専用の例外の型の定義(現在のC11は`verifyPasswordHash`がbooleanのみを返す) | NFR1.3 |
| 4 | C5 各API | 413(リクエストボディが64KiBを超えた場合)の追加 | security-requirements.md NFR2.3 |
| 5 | C5 招待API | 招待の同時実行数の上限超過・ロック待ちタイムアウトを表す503と、招待中でなくなった再招待の422(既存のValidationErrorを使用)の整理 | reliability-requirements.md NFR4.2 |
| 6 | C5 ProblemDetails | `errors[].message`をi18nキーで表す場合のキーの命名・パラメータの持たせ方 | NFR7.2 |
| 7 | 機能設計 BR4.15 | nameに制御文字(CR/LFなど)を含めない検証の追加 | security-requirements.md NFR2.7 |

## NFR8.1: 保守性(業務固有情報のハードコード禁止)

user-managementはUser・UserPreference・UserChangedEventのみを扱い、業務固有のテーブル名・カラム名・業務ルールをコードに持たない(functional-design rules.md BR4.14、要件のNFR8・FR1.6、project.md Mandated)。招待メールの文面は、コードに埋め込まずテンプレートとして外部に持つ。

## NFR8.2: テスト要件

- team.mdの既定に従い、**80%行カバレッジ**をCIでのマージ前実行で確保する。
- 認可の拒否(権限が不足する操作が確実に拒否されること)を狙う専用テスト(team.mdの必須テスト種別(c))を、次の観点で用意する: `/api/users`系の403・401(rules.md BR4.10)、自分自身のroleIds変更の拒否(BR4.12)、`/api/me/preferences`が他人の設定を操作できないこと(BR4.8)。
- 招待受諾の並行実行(NFR4.1)、メール送信失敗時のロールバック(NFR4.2)、同一emailの同時招待と、再招待と受諾・取消の競合(NFR4.2)、ハッシュ計算の同時実行数の上限と503(NFR1.3)を、テストの対象にする。
- セキュリティ要件を検証するテスト(team.mdの必須テスト種別(c)の趣旨を、認可以外にも広げたもの)を用意する。
  - パスワード・招待トークン・passwordHashが、レスポンス・ログ・トレースのスパン・メトリクスのラベル・監査イベントに現れないこと(NFR2.2・NFR2.10)。
  - パスワード長の境界値(7・8・128・129文字、サロゲートペアを含む文字列でのコードポイント数)(NFR2.3)。`verifyPasswordHash`が129文字以上をハッシュ計算せずにfalseとすること。
  - 未知・使用済み・取消済みの招待トークンが、いずれも同一の404になること(NFR2.4)。
  - 招待メールのHTMLエスケープ、および件名の抽出(文字参照のデコード後の改行の拒否、最大長)(NFR2.7)。
  - リクエストボディが64KiBを超える場合に413となること(NFR2.3)。
- NFR1.2(ハッシュ計算がp95で300ms以下)は、ハッシュ計測の単体ベンチマークテストで確認する。NFR1.1(3秒p95)は、team.mdが負荷・性能テストを既定に含めないため、自動検証はせず、統合テストの応答時間の記録による目視確認とする(performance-requirements.md)。
- 設定定義の誤り(初期管理者のemail・パスワードの未設定や長さの違反、SMTP設定、招待リンクのベースURL、メールテンプレートに`<title>`が無い場合)が、起動時にfail fastすることを確認する安全失敗のテスト(team.mdの必須テスト種別(a))を用意する。
- 監査ログの完全性の網羅的検証テストは、本MVPスコープでは必須としない(team.md確定事項)。

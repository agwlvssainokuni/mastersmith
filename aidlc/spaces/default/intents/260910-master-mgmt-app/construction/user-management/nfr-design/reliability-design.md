# Reliability Design — user-management (U4)

`nfr-requirements/reliability-requirements.md`の各要件を、設計に落とし込む。

## 資源の取得順序(全体の不変条件)

デッドロックや、資源の取り合いによる待ちを避けるため、次の順序を、user-managementのすべての処理で守る。

1. **排他(同一email)→ 許可(招待の同時実行数・ハッシュ計算)→ DB接続(トランザクション)** の順に取得し、逆順には取らない。
2. **ハッシュ計算の許可を保持している間は、DB接続を取らない**。**DB接続(トランザクション)を保持している間は、ハッシュ計算の許可を取らない**。ハッシュの計算は、必ずトランザクションの外側で行う。
3. 排他と許可の取得・返却は、トランザクションを張る側(`TransactionTemplate`を使うファサード)の**外側**で行い、コミットが終わってから返却する。`@Transactional`の付いたメソッドの内側では、排他・許可を取らない。

## NFR4.1: 招待受諾の原子性と、更新の競合

**招待受諾(`InvitationAcceptService`)の順序**(認証不要のAPIであり、未知のトークンでハッシュ計算の資源を消費させないため):

1. トークンで、Userを検索する(トランザクションの外の、軽い読み取り)。見つからない、またはstatusがinvitedでない場合は、ハッシュ計算をせずに404(使用済み・取消済み・未知を区別しない)。
2. パスワードの長さ(8〜128)・氏名・表示設定の値を検証する(422)。
3. ハッシュ計算の許可を取り、パスワードをハッシュ化して、許可を返す(performance-design.md NFR1.3)。
4. `TransactionTemplate`でトランザクションを開始し、次を行う。
   - トークンとstatus=invitedを条件に、Userを条件付きで更新する(status=active、passwordHashとnameを設定、invitationTokenをnullにする)。更新件数が0件なら、ロールバックして404。
   - UserPreferenceを作成する(BR4.3)。
5. コミットする。コミット後に、UserChangedEvent(ACTIVATED)を発行する(NFR4.3)。

```sql
-- 概念(実装はCode Generation): 更新件数で成否を判定する
UPDATE users SET status='active', password_hash=?, name=?, invitation_token=NULL
 WHERE invitation_token=? AND status='invited'
```

同一トークンの同時受諾では、手順1・3を両方が通っても、手順4の更新件数が1件になるのは一方だけで、他方は0件となり404になる(ハッシュ計算は、同時受諾の数だけ行われるが、許可の上限で制御される)。

**ユーザー情報の更新・無効化**: 対象のUser行を、トランザクションの中で**行ロック付きで読み取り(`SELECT … FOR UPDATE`相当、悲観的な書き込みロック)**、その値をbeforeValueとして、更新を適用する。同一Userへの更新・無効化は、行ロックにより直列化されるため、後勝ち(last-write-wins)の方針(楽観ロックは導入しない)のまま、beforeValueが常に直前の確定した値になる。

## NFR4.2: 招待の整合性(メール送信・競合)

招待(W1)は、トランザクションを張らない外側のファサード(`InvitationFacade`)が、次の順序で進める。

```
 [トランザクションの外側]
 1. 正規化後emailの排他を取る(EmailLockRegistry、最大12秒待つ)   … 取れなければ503
 2. 招待の同時実行数の許可を取る(InvitationAdmission、待たずに取得を試みる) … 満杯なら排他を返して503
 [TransactionTemplateの内側(トランザクション)]
 3. emailで既存を検索 → なし: 作成 / invited: 再招待として条件付き更新 / active・disabled: 422
 4. roleIdsの実在を検証(422)
 5. メール送信(InvitationMailExecutorのスレッド、呼び出し側が10秒で打ち切る)
                                                   … 失敗: ロールバックして503
 6. コミット
 [トランザクションの外側]
 7. 許可・排他を返す(finallyで必ず返す)
 8. コミット後に、UserChangedEvent(INVITED)を発行(NFR4.3)
```

- **排他を先に、許可を後に取る理由**: 同一emailの待機者が、許可を占有しないため。同一emailへの連打で許可が使い切られて、他のemailの招待が503になることを防ぐ。待機者は、Tomcatのリクエストスレッドだけを占有する(最大12秒)。
- **排他の管理(`EmailLockRegistry`)**: 正規化後emailをキーにした、参照数つきのロックの表(`ConcurrentHashMap`のエントリが、ロックと参照数を持つ)。利用者がいなくなった(参照数が0)エントリは、表から取り除く。ストライプ方式(ハッシュで固定数のロックに割り当てる)は、別のemailどうしが直列化されるため採らない。
- **同時実行数の許可(`InvitationAdmission`)**: 上限5の`Semaphore`。取得は、待たない(`tryAcquire`)。DB接続を占有するSMTP応答待ちの招待を、同時に最大5件に限る。
- **保持時間の上限**: 手順3〜6のトランザクションは、SMTPの打ち切り(10秒、performance-design.md NFR1.4)にDB処理の時間を加えた、概ね12秒以内に終わる。
- **同一emailの同時招待**: 排他により直列化される。後から入った側は、先行がコミットした結果を見て、再招待(invited)または重複(422)として処理する。排他を12秒待って取れない場合は、503。
- **排他をすり抜けた場合**(複数プロセス構成など): DBの一意制約違反は422(フィールド単位)、DBのロック待ちタイムアウトは503に変換する。500にはしない。
- **再招待と、受諾・取消の競合**: 再招待の更新は、status=invitedを条件とする。条件を満たさなくなった(受諾または取消された)場合は、再招待側に422(このemailのユーザーは、すでに招待中ではない)を返す。
- **進行中の再招待と、受諾・取消・更新**: 再招待のトランザクションが未コミットの間に、同じUserに対する受諾・取消・更新が来た場合は、DBの行ロックで待たされる。ロック待ちがタイムアウトした場合は503(再試行してもらう)。
- **送信成功後にコミットが失敗した場合**: メールは届くが、トークンは無効になる。管理者が再招待して解消する。専用の補償処理は設けない。
- **打ち切り後の送信スレッド**: 呼び出し側がメール送信を打ち切っても、送信のスレッドは、ブロッキングI/Oの途中では止められないため、しばらくプールを占有し続けうる。その間の新しい招待は、プールが満杯であれば、投入時の拒否(`RejectedExecutionException`)を503に変換する。また、打ち切り後に送信が完了すると、ロールバック済みで存在しないトークンのリンクを含むメールが届きうる(そのリンクは、受諾時に404になる)。これは制約として受け入れ、残余リスク7に記録する(security-design.md)。

**方式の選定**: 「確定保存してからメールを送り、失敗したら補償処理で巻き戻す」方式は、SMTP応答待ちの間のトランザクション保持を避けられるが、補償の失敗でUserが残り、BR4.16の「失敗時は招待全体を巻き戻す」の保証が弱まる。上記のとおり、保持時間の上限と、同時実行数の上限で制御できるため、BR4.16を保つ現方式を採る。

**内部設定DBの接続プール**: 招待は、最大5件が、約12秒ずつ接続を保持しうる。接続プールの最大サイズは、通常の同時処理数(要件のNFR1の同時アクセス最大50ユーザー)に、招待の上限5を加えた値以上とする(具体的な値は、共通基盤の設計で確定する。共有するリソースのため、logical-components.mdの「共通基盤への要求」に記録する)。

## NFR4.3: 監査イベントの配信(コミット後・独立したトランザクション・fire-and-forget)

- `UserChangedEventPublisher`が、トランザクションの**コミットが成功した後に**(トランザクション同期の`afterCommit`で)、UserChangedEventを発行する。コミットに失敗した場合・ロールバックした場合・招待メールの送信に失敗して巻き戻した場合は、発行しない。
- **受信側の書き込みを確定させる**: `afterCommit`の時点では、元のトランザクションはすでにコミット済みで、受信側(audit-logging)が「既存のトランザクションに参加する」設定で書き込むと、その書き込みは、以降コミットされず、失われる。これを避けるため、発行側が、**新しい独立したトランザクション(`TransactionTemplate`の`REQUIRES_NEW`)の中で**、同期の`ApplicationEventPublisher.publishEvent`を呼ぶ。受信側(同期の`@EventListener`)の書き込みは、この新しいトランザクションに参加し、発行側が抜けるときにコミットされる。
- **発行側の例外の捕捉**: この発行全体(新しいトランザクションの開始からコミットまで)を、`try-catch`で囲む。例外が起きても、警告ログ(userIdのみ)とメトリクス(observability-design.md NFR5.1の`user.event.publish.failed`)に記録し、HTTPの結果には影響させない(コミット済みでメール送信済みの招待が、500で返ることを避ける)。
- 受信側は、他ユニットと同じ、同期の`@EventListener`と、例外を発行元に伝えないtry-catchの境界で受ける。配信の再送や、At-Least-Onceの保証は、本MVPでは設けない(他ユニットと同じ方針。監査ログの記録に失敗しても、User更新は失敗しない)。
- **受信側への前提(契約追補・保留)**: 上記の方式は、受信側が同期の`@EventListener`で、呼び出し元のトランザクションに参加して書き込むことを前提とする。共有契約には、受信側のトランザクションの扱いの定めがないため、audit-loggingへの要求として、logical-components.mdの「共通基盤・他ユニットへの要求」に記録する。
- 1回の操作につき、イベントは1件(BR4.9)。冪等な再実行(すでにdisabledへの再DELETE)では発行しない。ログイン成功時のハッシュ更新(security-design.md NFR2.2)は、イベントの対象外。
- **検証**: コミット後の発行で、監査ログの行が実際に永続化されること(発行後に、別のトランザクションから読める)を、統合テストで確認する(logical-components.md NFR8.2)。

## NFR4.4: 起動時の初期管理者作成

- `InitialAdminBootstrap`(`ApplicationRunner`)は、パスワードのハッシュ計算を、トランザクションの外側で先に行い、そのあと、対応するUserの有無の確認と作成を、1つのトランザクションで行う(資源の取得順序の不変条件)。既に存在すれば、何もしない(冪等。ただし、ハッシュ計算は、存在を先に確認してから行い、存在する場合は行わない)。
- 起動のたびに実行されるため、並行して複数のプロセスが起動した場合は、emailの一意制約違反になりうる。その場合は、違反を「既に存在した」として扱い、何もしなかったこととする。
- 設定の不備は、プロパティのバインド時に検知して、起動を失敗させる(security-design.md NFR2.11)。

## NFR4.5: 可用性・バックアップ・障害時の縮退

- 可用性とバックアップ・リカバリは、アプリケーション本体(単一WAR)と、内部設定DB全体に従う。本ユニット固有の追加要件はない。
- **障害時の影響の範囲**:

| 障害 | 影響 | 縮退 |
|---|---|---|
| SMTPの不調・遅延 | 招待・再招待が503で失敗する。招待が、最大5件まで、約12秒ずつ内部設定DBの接続を保持する | 接続プールに余裕がある限り(上記の最大サイズ)、他の機能(一覧・更新・無効化・受諾・ログイン)は影響を受けない。プールに余裕がない場合は、他の機能も接続待ちになりうる。失敗はカウンタで検知する |
| ハッシュ計算の混雑 | 招待受諾・ログイン(C11)・初期管理者の作成が、待機2秒で503になる | 他の機能は影響を受けない(ハッシュ計算の許可は、DB接続を保持しない) |
| 同一emailの連打 | 同じemailの招待だけが、順番待ち・503になる | 他のemailの招待は、許可を占有されないため影響を受けない(排他を先に取る) |
| 内部設定DBの障害 | user-managementのすべてが使えない | ヘルスチェック(observability-design.md NFR5.4)で検知する。アプリケーション全体の障害として扱う |

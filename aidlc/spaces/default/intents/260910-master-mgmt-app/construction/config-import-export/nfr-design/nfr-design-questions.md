# NFR Design Questions — config-import-export (U9)

`construction/config-import-export/nfr-requirements/`(NFR1.1〜NFR8.1)、`functional-design/`(functional-spec.md・rules.md)、`inception/contract-design/contract-summary.md`(C7・C9・C10・C12)に基づき、config-import-exportのNFRを実現する設計の方式を決めるための質問。

NFR Requirementsで確定した事項(性能目標・受け入れたリスク・時間上限なし・標準の計装と開始・終了ログ)は、再確認しない。設計の中で、対応が一意に定まる事項は、質問せずに、設計書に決定として記録する。具体的には次のとおり。

- リクエスト本体は、Jackson(`jackson-databind`、既存の依存)で木構造(`JsonNode`)として読む。検証の誤りの位置は、JSON Pointer(例: `/schema/tables/0/columns/3/columnName`)で表す。
- 取り込みの反映は、3つのユニットが共有するSpringのトランザクション1つで行う。削除は、依存の逆順(権限→メニュー→ロール・グループ→カラム・テーブル・翻訳)で先に行い、追加・更新は、依存の順(schema→ロール・グループ→メニュー→権限)で行う(機能設計のレビュー指摘R-06への対応)。
- 現在の設定の読み込みは、自然キーをキーにしたマップにして、検証・差分の計算でN+1の問い合わせを避ける。書き込みは、まとめて行う(バッチ)。
- エクスポートの読み取りは、H2の`REPEATABLE_READ`(H2 2.4.240で、スナップショット分離に相当するMVCCの読み取り。Spring Boot 4.1.1の依存管理のバージョンで確認済み)の読み取り専用トランザクションで行う(NFR4.4)。H2の既定のロック待ちは2秒(`INITIAL_LOCK_TIMEOUT`=2000ms)であり、他の管理操作と取り込みが衝突して、ロックを2秒待っても取れなければ、503になる(NFR4.3)。
- エクスポートの`appVersion`は、Spring Bootのビルド情報(`BuildProperties`)から取る。
- 内部設定DBのH2ファイルの退避(バックアップ)を、取り込みの前の運用手順に含める(NFR4.7の追補。機能設計のレビュー指摘の自己の締め出しへの備え)。

## Q1: コミット後のキャッシュ再構築が失敗したときの扱い

取り込みは、トランザクションの確定後に、3つのユニットのキャッシュを再構築し、変更イベントを発行します(NFR4.2)。確定後は、内部設定DBの内容をロールバックできません。このときにキャッシュの再構築が失敗すると(たとえば、メモリ不足や、再読み込み中のDBの障害)、内部設定DBは新しい設定なのに、キャッシュが古い設定のまま、という食い違いが残ります。応答をどう返すか、食い違いをどう扱うかを決めます。

- A. 再構築を1回だけ再試行し、それでも失敗したら、応答は200(DBは確定済みで、取り込みとしては成功)のまま、ERRORのログを出す。Actuatorのヘルスチェックに、「設定のキャッシュが、内部設定DBと食い違っている可能性がある」ことを、DOWNとして示す。復旧は、アプリケーションの再起動による(起動時に、DBから全件を読み込む)。取り込みの監査イベントは、成功として発行する(備考として、再構築の失敗を、ログに残す)
- B. 応答を500にし、取り込みの監査イベントは、UNEXPECTEDの失敗として発行する。ただし、DBは確定済みで、新しい内容になっている(応答と、実際の状態が食い違う)。利用者には、再度の取り込みか、再起動を促す
- C. 各ユニットのキャッシュを、確定後に「再構築」するのではなく、「無効化」する方式にそろえる。次の読み取りで、内部設定DBから遅延して読み込む。再構築の失敗という状況が、取り込みの中では起きなくなる(次の読み取りが失敗した場合は、その読み取りが503になる)。config-engine・menu-navigation・permission-engineのキャッシュに、無効化と遅延の読み込みの仕組みを、追加で実装する必要がある(現状は、起動時の全件読み込みと、書き込み時の更新が前提)
- X. Other (please specify)

[Answer]: C. 各ユニットのキャッシュを、確定後に「再構築」するのではなく、「無効化」する方式にそろえる。次の読み取りで、内部設定DBから遅延して読み込む。再構築の失敗という状況が、取り込みの中では起きなくなる(次の読み取りが失敗した場合は、その読み取りが503になる)。config-engine・menu-navigation・permission-engineのキャッシュに、無効化と遅延の読み込みの仕組みを、追加で実装する必要がある(現状は、起動時の全件読み込みと、書き込み時の更新が前提)

## Q2: エクスポートの読み取り元(内部設定DBか、各ユニットのキャッシュか)

NFR4.4は、エクスポートを、読み取り専用のトランザクション(`REPEATABLE_READ`)で、取り込みの反映の途中の状態を読まないようにします。ただし、config-engine(と、menu-navigation・permission-engine)の`getExportable〜`は、現状、インメモリのキャッシュから読む実装です。キャッシュから読むと、3つのユニットのキャッシュは、それぞれ別のタイミングで再構築されるため、取り込みの確定の直後に、ユニットどうしで新旧の内容が混ざったエクスポートが、ごく短い間だけ、生じうる余地があります(スナップショット分離は、キャッシュには効きません)。

- A. 3つのユニットの`getExportable〜`を、キャッシュではなく、内部設定DBから直接読む方式に改める(エクスポートの読み取り専用トランザクションの中で読む)。エクスポートの一貫性が、DBのスナップショットで担保される。3つのユニットに、キャッシュを介さない読み取りの経路を追加する必要がある(エクスポートは低頻度のため、DBを引く負荷は問題にならない)
- B. `getExportable〜`は、現状どおり、キャッシュから読む。3つのユニットのキャッシュの再構築が、確定後に、続けて行われるため、混ざりうる余地は、ごく短い間に限られるとして受け入れる。実装の変更は少ないが、NFR4.4の「1つの時点として整合する」が、キャッシュの再構築の間は、保証されない。あわせて、キャッシュ内のインスタンスを、他から変更できないコピーとして返す実装が必要になる
- X. Other (please specify)

[Answer]: A. 3つのユニットの`getExportable〜`を、キャッシュではなく、内部設定DBから直接読む方式に改める(エクスポートの読み取り専用トランザクションの中で読む)。エクスポートの一貫性が、DBのスナップショットで担保される。3つのユニットに、キャッシュを介さない読み取りの経路を追加する必要がある(エクスポートは低頻度のため、DBを引く負荷は問題にならない)

## Q3: 認可と、リクエスト本体の読み取りの順序

NFR Requirementsのレビュー指摘は、次を挙げました。インポートは、リクエスト本体の大きさに上限がなく(NFR2.2)、認可の判定(`canAccessScreen`)が、本体の読み取りよりも後になると、権限のない認証済みの利用者でも、巨大な本体を送って、メモリを使わせられます(NFR2.2の「権限を持つ操作者に限られる」という前提が崩れます)。Springの通常の`@RequestBody`は、コントローラーのメソッドが呼ばれる前に、本体を全件読み込んで解析します。

- A. 認可を、本体の読み取りより前に行う。インポートのコントローラーは、`@RequestBody`を使わず、`HttpServletRequest`の入力ストリームを受け取り、(1)操作者の解決(401)、(2)`canAccessScreen`(403)を行ってから、はじめて、Jacksonで本体を読む。認可に失敗したら、本体を1バイトも読まずに、401・403を返す。本体は、認可の後に、全件を読む(大きさの上限は置かない。NFR2.2)
- B. 通常の`@RequestBody`(`JsonNode`)の束縛を使い、コントローラーのメソッドの中で認可する。実装は、他のコントローラーと同じで単純だが、認可の前に、本体が全件読み込まれる。権限のない認証済みの利用者から、メモリを消費させられる余地が残る(NFR2.2の残余リスクに、この経路を追記する)
- X. Other (please specify)

[Answer]: B. 通常の`@RequestBody`(`JsonNode`)の束縛を使い、コントローラーのメソッドの中で認可する。実装は、他のコントローラーと同じで単純だが、認可の前に、本体が全件読み込まれる。権限のない認証済みの利用者から、メモリを消費させられる余地が残る(NFR2.2の残余リスクに、この経路を追記する)

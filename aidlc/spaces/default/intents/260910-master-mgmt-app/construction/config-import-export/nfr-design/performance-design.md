# Performance Design — config-import-export (U9)

`nfr-requirements/performance-requirements.md`(NFR1.1〜NFR1.3)と、`nfr-design-questions.md`の確定回答(Q2=A)に基づく、config-import-exportユニットの性能設計。本ユニットは、設定を扱う低頻度の管理者操作であり、キャッシュや非同期処理は設けない。

## 設計方針

- 設定は、想定規模の上限(NFR1.3)でも、数MB以下である。全体を、メモリ上で処理する(ストリーミングは行わない)。
- 性能上の要点は、問い合わせの回数(N+1を避ける)と、書き込みのまとめ方(バッチ)の2点に絞る。

## NFR1.1: エクスポートの設計(3秒以内、p95)

| 段階 | 方式 |
|---|---|
| 読み取り | 読み取り専用のトランザクション(`REPEATABLE_READ`)を1つ開き、config-engine・menu-navigation・permission-engineのエクスポート用メソッドを、その中で呼ぶ。3ユニットとも、キャッシュではなく、内部設定DBから直接読む(Q2=A) |
| 問い合わせの数 | 各ユニットは、テーブルごと・カラムごとの問い合わせをせず、対象の種類ごとに全件を1回で読む(テーブル・カラム・翻訳・メニュー項目・ロール・グループ・グループとロールの対応・主権限・補助権限の、9種類程度の一括の取得)。カラムなどの、親との結びつけは、メモリ上のマップで行う |
| 変換 | 内部IDから自然キーへの変換は、IDをキーにしたマップで行う(親の名前の解決で、再度DBを引かない) |
| 出力 | ConfigDocumentを、Jacksonで、レスポンスのストリームへ直接書き出す(いったん文字列にまとめない) |

- **見積もり**: 想定規模の上限(NFR1.3)で、一括の取得9回程度、行数の合計は約1.5万行。H2(ファイルモード)で、数百ミリ秒の見込み。3秒(p95)に対して、十分な余裕がある。

## NFR1.2: インポートの設計(10秒以内、p95)

| 段階 | 方式 | 予算(想定規模の上限) |
|---|---|---|
| (1)本体の読み取りと構文の確認 | Spring MVCが、本体を`JsonNode`として読む(Q3=B)。構文の誤りは、ここで検出する | 0.5秒 |
| (2)構造・参照整合の検証 | ConfigDocumentへの変換と、構造・参照整合の検証を、メモリ上で1パスで行う。誤りは、上限(100件)まで集める | 0.5秒 |
| (3)現在の設定の読み込み | 検証・差分の計算のために、3ユニットの現在の設定を、エクスポートと同じ、一括の取得で読む。取り込みのトランザクション(`REPEATABLE_READ`。reliability-design.md NFR4.1)の内側で、キャッシュを介さず、内部設定DBから直接読む | 0.5秒 |
| (4)各ユニットの検証 | 各ユニットの検証専用メソッドが、メモリ上のマップで、自然キーの照合と、規則の検証を行う。DBへの問い合わせは、(3)で読んだ内容の範囲を超えて行わない | 1秒 |
| (5)反映 | 削除→追加・更新の順に、まとめて書き込む(バッチ)。Hibernateのバッチ設定(`hibernate.jdbc.batch_size`=50、`order_inserts`・`order_updates`=true)を、内部設定DBのデータソースに設定する。1件ずつの`save`と`flush`を繰り返さない | 5秒 |
| (6)確定後の処理 | キャッシュの無効化(メモリ上のフラグの設定だけ)と、イベントの発行 | 0.1秒 |
| 合計 | | 7.6秒(目標の10秒に対して、余裕2.4秒) |

- **バッチの設定は、既存のユニットのデータソース設定に影響する**: `hibernate.jdbc.batch_size`などは、アプリケーション全体の設定であり、他のユニットの書き込みにも適用される。Code Generationで、既存の設定の有無を確認し(現時点の`application.yml`には、`hibernate.jdbc.batch_size`の設定がないことを、アーキテクチャレビュー iteration 1で確認)、追加する場合は、他のユニットのテストが、そのまま成功することを確認する。
- **バッチが有効になる前提の確認(Code Generationの確認項目)**: 主キーの生成方式が`IDENTITY`の場合、Hibernateは、挿入のバッチを無効にする。対象のエンティティの、主キーの生成方式を確認し、`IDENTITY`であれば、(a)生成方式の変更(シーケンスなど)が可能か、(b)`JdbcTemplate`のバッチ更新で、挿入を行うか、を、Code Generationで決める。挿入のバッチが効かない場合、(5)の5秒の予算の前提が崩れるため、実測で再確認する。
- **段階の境界での`flush()`**: 反映の各段階の境界で、明示的に`flush()`する(reliability-design.md NFR4.1)。`flush()`は、バッチの単位を分けるが、段階の数(8)が少ないため、性能への影響は小さい。
- **予算の根拠**: 各段階の値は、行数(想定規模の上限で、合計約1.5万行)と、H2(ファイルモード)の一般的な処理の速さからの**見積もり**であり、過去の同種の処理の実測・保証ではない。Build and Testの実測(下の「性能の確認の設計」)で、置き換える。

## NFR1.3: 想定規模

想定規模の上限(テーブル100、カラム約3,000、翻訳約6,000、ロール50、主権限約5,000)を、性能確認用のテストデータ(フィクスチャ)の生成器として実装する。業務固有の名前は使わず、連番から機械的に生成する(NFR8.1・BR9.20)。

## 性能の確認の設計(NFR1.1・NFR1.2)

NFR Requirementsのレビュー指摘(測定方法に、試行回数・環境・ウォームアップがない)に対応して、次のとおり定める。

| 項目 | 定義 |
|---|---|
| 環境 | CIと同じ構成(内部設定DBはH2のファイルモード、単一プロセス)。実行環境のCPU・メモリを、結果と一緒に記録する |
| ウォームアップ | 計測の前に、5回、実行して捨てる(JITの最適化・接続の確立) |
| 試行 | 計測は、30回。同時に実行するのは、1件。NFR1.1・NFR1.2の負荷条件「同時に1〜2件」のうち、2件の同時は、別に3回、実行する。3回では、p95を定義できないため、**3回とも目標以内**を合格とする |
| 取り込み直後の最初の読み取り(Q1=C。確定後の再読み込み) | 取り込みの直後に、ほかのユーザーの、最初の読み取り(認可の判定・設定の取得など、キャッシュを使う読み取り)が、再読み込みの時間を負担する。取り込みの後の、最初の読み取りを、10回計測し、**最大値が、NFR1の3秒以内**を合格とする |
| 判定 | 30回の、95パーセンタイル(最近順位法。小さい方から`ceil(0.95×30)`=29番目の値)が、目標(エクスポート3秒、インポート10秒)以内 |
| 位置づけ | 高負荷・性能テスト(team.mdの「負荷・性能テストは既定には含めない」)ではなく、`team.md`の「確認済み品質目標の充足を検証する」に基づく、NFRの確認である。単一の利用者による繰り返しの実行であり、負荷の掛け方は含めない |

## 性能に関する除外(Performance Anti-Requirements)

- 「エクスポート・インポートは高速でなければならない」のような、測れない表現は使わない。目標は、NFR1.1・NFR1.2の数値のみ。
- 取り込みの結果のキャッシュや、非同期化は行わない。応答は、取り込みの完了後に、同期的に返す。
- 実行時間の上限(タイムアウト)は設けない(NFR4.3)。

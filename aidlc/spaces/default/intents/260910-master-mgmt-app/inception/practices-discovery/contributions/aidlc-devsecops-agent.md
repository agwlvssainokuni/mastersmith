## Contribution

DevSecOps(セキュリティ/セキュリティパイプライン)観点でドラフト一式(`team-practices.md`
/ `discovered-rules.md` / `evidence.md`)をレビューした。ドラフトは `org.md` の5セクション
(Way of Working / Walking Skeleton / Testing Posture / Deployment / Code Style)を出発点として
妥当に転記しており、それ自体に誤りはない。ただし、本プロジェクトのMVPスコープには
ユーザ管理・監査ログ・詳細RBAC(ロール階層継承、FULL/READ/NONE主権限、CREATE/DELETE補助権限)
が含まれるにもかかわらず、セキュリティ関連のプラクティス(静的/動的解析、シークレット
スキャン、依存関係・サプライチェーン管理、および認可・監査ログのハード制約)が
ドラフトのどのセクションにも存在しない。以下を補うことを提案する。

### 1. Lint/Format(Code Styleセクションへの補足)

- ドラフトの「フォーマッタ/リンタはプロジェクトルート設定に委譲」という方針自体は妥当。
  ただし技術スタックが未確定の現段階では、フォーマッタ/リンタの選定に加えて
  **セキュリティ寄りの静的解析ルール**(例: ESLintのセキュリティ系プラグイン、
  `bandit`、`gosec` 等、言語確定後に選定)をCIのブロッキングチェックに含めるかどうかを
  未決事項として明示すべきである。現ドラフトはこの観点が抜けている。

### 2. SAST / DAST(新規セクション、または Deployment/Code Styleへの追記)

- SAST(静的アプリケーションセキュリティテスト)・DASTのいずれもドラフトに記載がない。
  本プロジェクトはRBAC・監査ログを持つ社内業務アプリであり、認可バイパスや入力検証不備の
  影響が大きいため、以下をインタビューで確認しCI/CDパイプラインのプラクティスとして
  記録することを提案する。
  - SAST: 技術スタック確定後、CIのマージ前チェックとして導入するか(例: CodeGuru Security、
    SonarQube、Semgrep)。少なくとも「導入する/しない」をチームとして明示的に決定すべき。
  - DAST: MVPのリリース前、または `4.x` 系オペレーション系ステージ実施時
    (現状SKIP)に、認可制御(RBAC)・認証まわりを対象とした動的スキャンないし
    手動ペネトレーションテストを実施するかどうかを later stage(NFR設計・
    infrastructure-design等)への申し送り事項として記録する。

### 3. シークレットスキャン・依存関係/サプライチェーン管理(新規、Code Style/Deploymentへの追記)

- `construction.md`(フェーズガードライン)の「Security」節に
  「認証情報・APIキー・シークレットのハードコード禁止、環境変数またはシークレットマネージャを
  使用」との既定はあるが、これを**CIで機械的に検証する仕組み**(シークレットスキャン、
  例: `gitleaks`/`trufflehog` 等)がteam-practicesに記載されていない。マージ前ゲートとして
  追加することを提案する。
- 依存関係の脆弱性スキャン(`npm audit`/Dependabot/Snyk/Amazon Inspector等、技術スタック
  確定後に選定)およびSBOM生成についても、Code Style節の「フォーマッタ/リンタ」と並ぶ
  CIゲートとして明記すべきである。現ドラフトはテストカバレッジ・リンタのみをゲートとして
  挙げており、依存関係監査は抜けている。

### 4. RBAC/監査ログに関するハード制約の候補(discovered-rules.mdへの追加候補)

`discovered-rules.md` は人間の明示発言がないためMandated/Forbidden空欄というスタンスは
手続き上正しい。その上で、本MVPスコープの性質(RBAC・監査ログ・ユーザ管理)を踏まえ、
以下をインタビューでの確認候補として提示することを提案する(いずれも人間が明示的に
肯定した場合のみ `discovered-rules.md` へ計上する)。

- ALWAYS 候補: 認可判定はクライアント側のUI非表示だけに依存せず、必ずサーバー側(API/
  ドメイン層)で権限(ロール階層継承後の実効権限)を再検証する。
- ALWAYS 候補: 監査ログは改ざん・削除不可(追記専用、アプリケーションからのUPDATE/DELETE
  経路を持たない)とし、少なくとも「操作者・操作対象・操作種別・日時・変更前後の値」を
  記録する。
- ALWAYS 候補: パスワード等の認証情報はハッシュ化(bcrypt/argon2等)して保存し、平文で
  ログ・監査ログ・エラーメッセージに出力しない。
- NEVER 候補: ロール/権限の昇格(自己昇格を含む)を、明示的な権限管理者操作を経ずに
  許可しない。
- NEVER 候補: シークレット・認証情報をリポジトリやドキュメント(このドラフト含む成果物)
  に平文で記載しない(`construction.md` 既定の再確認・CI強制化)。

これらは本ステージのインタビューステップで人間に問い、明示的な同意が得られたものだけを
`discovered-rules.md` の `## Mandated` / `## Forbidden` へ反映されたい。

## Positions
- AGREE: Way of Working / Walking Skeleton / Deployment節の内容(トランクベース、Squash-merge、Bolt運用、staging自動デプロイ+production手動承認)はセキュリティ上の懸念がなく、org.md既定をそのまま出発点とすることに問題はない — 変更管理・デプロイフローの慎重さと監査ログによる補完は妥当な設計。
- OBJECT: ドラフトのCode Style/Testing Posture節にSAST・DAST・シークレットスキャン・依存関係/サプライチェーンスキャンの記載が一切ない — RBAC・監査ログ・ユーザ管理をMVPスコープに含む本プロジェクトでは、これらのセキュリティパイプライン統合をチームプラクティスとして明示的に検討・記録すべきであり、抜け落ちるとConstructionフェーズでのセキュリティゲート設計が後手に回る。
- OBJECT: `discovered-rules.md` が完全に空欄のままインタビューへ進む計画になっているが、RBAC/監査ログ/認証情報の扱いに関する具体的なALWAYS/NEVER候補(本ファイル「Contribution」節の4.参照)を人間に提示せず「他にありますか」とオープンに問うだけでは、重要なハード制約の見落としリスクがある — 候補を挙げた上でYes/Noを問う形にすべき。

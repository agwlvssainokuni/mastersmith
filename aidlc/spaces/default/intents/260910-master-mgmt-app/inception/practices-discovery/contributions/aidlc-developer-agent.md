## Contribution

開発者/コードスタイルの観点から `team-practices.md`(ドラフト)を精査した。org.md 既定値の転記としては妥当だが、MasterSmith の性質(設定駆動型マスタ管理エンジンであり、単一アプリを設定の入れ替えだけで複数業務に転用する)を踏まえると、レイヤー境界・エラーハンドリング・ファイル構成・命名規約の4点で具体的な補足とインタビュー項目の追加が必要と考える。

### 1. 技術スタックが未決定であることの扱いを明確にすべき

`team-practices.md` の Code Style 末尾に「技術スタック自体は本ステージ以前に確定していない」旨が一言記載されているが、これは単なる注記に留めず、インタビューの明示的な論点として扱うべきである。フォーマッタ/リンタの選定だけでなく、レイヤー境界の実装方法(モジュール分割 or パッケージ分割)、エラー型の設計(例外 vs Result型)、命名規約(camelCase/snake_case のどちらが既定になるか)は言語選定に強く依存する。技術選定そのものをこのステージのインタビューで扱うのか、後続の architecture/domain-design ステージに持ち越すのかを、`discovered-rules.md` またはインタビューの冒頭で人間に確認すべきギャップとして明示することを提案する。

### 2. レイヤー境界の規約がドラフトに存在しない

MasterSmith の成功定義は「単一アプリ本体を設定の入れ替えだけで複数業務のマスタ管理に転用できること」(project.md `## Decided`)である。この目的を実装レベルで守るには、以下のレイヤー境界を Code Style または新設の「Architecture」的な項目として team-practices.md に追加することを提案する。

- **汎用エンジン層**(一覧/詳細編集画面、権限判定(RBAC: 主権限FULL/READ/NONE/指定なし・補助権限CREATE/DELETE・階層継承)、監査ログ記録、ユーザー設定(テーマ/フォントサイズ)適用など)は、特定業務のテーブル名・カラム名・業務ルールをハードコードしない。
- **業務固有設定層**(表示名/表示順/書式/編集部品/バリデーション定義)は、エンジン層から読み込まれるデータとして扱い、コード変更なしに差し替え可能であることを規約として明文化する。
- この境界を破る変更(エンジン層に業務固有分岐を書く等)は、レビューでの明示的な指摘対象とすべきではないか、という点をインタビューで確認したい。

### 3. エラーハンドリング規約が Code Style に反映されていない

`aidlc/spaces/default/memory/phases/construction.md` のフェーズガードレール(このステージには直接適用されないが、後続のConstructionフェーズ全体に適用される)は「サイレント失敗の禁止」「回復可能エラーと致命的エラーの区別」「境界(API呼び出し・DB操作・ファイルI/O)での例外処理必須」を求めている。しかし `team-practices.md` の Code Style セクションにはエラーハンドリングへの言及が一切ない。設定駆動アプリでは特に、以下2種のエラーを区別する規約が必要と考える。

- **設定定義自体の不整合**(バリデーションルールの記述ミス、必須プロパティ欠落等) — 起動時/設定読込時に検知し fail fast する。
- **実行時のユーザー入力データ検証エラー** — エンドユーザーにフィールド単位のエラーメッセージとして返す(業務担当者が利用者であるため、開発者向けのスタックトレースをそのまま見せない配慮が必要)。

この区別を Code Style または新設項目として team-practices.md に追記することを提案する。

### 4. ファイル構成・命名規約への補足

- 設定(業務固有定義)の物理的な配置規約(例: `config/` ディレクトリ配下にテーブル定義ごとにファイル分割するか、単一ファイルにまとめるか)は技術選定時の論点として記録しておくべきである。また、project.md で既に `reference/`(Git管理外の参考資料置き場)が確定しているため、新設する設定ディレクトリ名がこれと混同されないよう命名する必要がある。
- RBAC 権限モデルの日本語ドメイン用語(ロール/主権限/補助権限/階層継承)とコード上の識別子(enum値・変数名等)のマッピングは、技術選定後に用語集(グロッサリー)として早期に合意しておくことを提案する。後続の domain-design / contract-design ステージでの用語のブレを防ぐ効果がある。

### 5. Testing Posture への補足コメント

test-after / 80%カバレッジフロア / マージ前CI という既定自体は開発者視点で妥当と考える。ただし、設定駆動エンジンの性質上、「エンジン層の共通ロジックに対する単体テスト」と「サンプル設定を用いた統合テスト(表示/権限判定/バリデーションが設定通りに動作することの確認)」は性質が異なるため、両者を区別したテスト設計方針をどこかの段階(build-and-test 等)で明文化する必要がある、という点を申し送りたい。本ステージの team-practices.md 自体への追記は必須とまでは考えないが、認識共有のため記録する。

## Positions

- AGREE: Code Style の「リンタで既にカバーされていない場合にのみ提案を適用する」という方針 — project.md で確定済みの規約(ライセンスヘッダー等)と重複せず整合している
- OBJECT: レイヤー境界(エンジン層/業務固有設定層の分離)に関する規約がドラフトに一切存在しない — 「設定の入れ替えだけで複数業務に転用できる」という本プロジェクトの成功定義を実装で守るための最重要規約が欠落している
- OBJECT: エラーハンドリング規約が Code Style に反映されていない — construction.mdフェーズガードレールが求める「サイレント失敗禁止」「回復可能/致命的の区別」が team-practices.md へ明示的に取り込まれておらず、Bolt実装時の参照先が曖昧なまま

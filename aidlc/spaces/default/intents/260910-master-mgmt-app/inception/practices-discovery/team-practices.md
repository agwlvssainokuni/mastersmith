## Way of Working

- トランクベース開発を採用する。すべての作業は短命なフィーチャーブランチ(目安1〜2日で解決)を経て
  `main` にマージする。長命ブランチはマージ負債を蓄積するため避ける。
- Constructionのworktreeは、ベースブランチを `main`、マージ先を `main` とする。
- 複数環境(staging/production)が必要になっても単一トランクを維持し、タグや環境別デプロイ設定で
  リリースを制御する。長命リリースブランチは用いない。
- BoltブランチはSquash-mergeで `main` に統合する。各Boltはトランク上で1コミットとなり、
  Boltスラッグを名前に用いる。Bolt元ブランチの詳細なコミット履歴は、worktreeを破棄するまで
  ソースブランチ上に保持する。
- Squash方式により `main` の履歴は delivery-planning のBolt順序と1:1に対応する線形なものになる。
  中間コミットが `main` 上から失われるトレードオフは、監査ログ(audit log)がイベント系列を
  完全に保持することで許容する。

(参考: `project.md` にはコミット運用・ライセンスヘッダー・パス表記など既に確定済みの
プロジェクト固有ルールがあり、これらは本ステージで再確認する対象ではない。)

## Walking Skeleton

- プラクティスがスコープ依存である場合、アクティブなスコープファイルが `skeleton: on` を
  宣言しているときに限り、walking-skeleton Boltを**最初**に実行する。Bolt 1は単独実行・
  ゲート付きとし、ユーザーが明示的に承認してから残りのBoltを実行する。
- アクティブなスコープファイルが `skeleton: off` を宣言している場合はスケルトン儀式を
  **省略**する。最初のBoltは他のBoltと同様に実行され、ブートストラップすべき対象がない。
- Bolt 1が完了した後(実行した場合)、オーケストレーターは**ラダープロンプト**
  (「残りのBoltはどのように進めるか?」)を提示する。選択肢は「自律的に継続する」
  「Boltごとにゲートする」であり、チームがプロジェクトごとに選択する。選択結果は
  `aidlc-state.md` の `Construction Autonomy Mode` として保持する。
- 本プロジェクトの `config-driven-admin-mvp` スコープでの `skeleton` 設定値、および
  ラダープロンプトの選択は、本ステージのインタビューステップで確認する。

## Testing Posture

- **Methodology**: test-after
- **Ordering**: 各テスト対象レイヤーを実装した後、そのレイヤーのテストを作成し実行する
  (実装 → 当該レイヤーのテスト作成・実行、という順序をレイヤーごとに繰り返す)。
- テストはすべてのBoltにおいて第一級の成果物として扱う。
- スコープ `config-driven-admin-mvp` は `mvp` 系のスコープ既定に準じ、80%の行カバレッジ
  フロアとマージ前のCI実行を追加で課す(org.md既定に基づく暫定値)。
- 適用中の Test Strategy(Comprehensive)がテストの分量・種別を規定する。スコープ側の
  フロアはこれに追加されるものであり、Test Strategyを弱めたり置き換えたりしない。
- Build and Test ステージは、定義済みカバレッジフロアと確認済み品質目標の充足を検証する。
  これらのステップを通過させるために基準を緩めることはしない。
- 本セクションの `Methodology` / `Ordering` および上記フロアは、org.md既定を出発点とした
  ドラフトであり、インタビューステップでチームの実態(TDD/BDD/ATDD選好の有無等)を
  確認したうえで最終確定する。

## Deployment

- マージ時にstaging環境へデプロイする(deploy on merge)。
- Production環境へのデプロイは、テックリードおよびプロダクトオーナーによる承認など、
  別途の手動承認をゲートとする(CodePipelineやCDプラットフォームの環境保護機能を想定)。
- テストカバレッジとオブザーバビリティに十分投資したチームは、Production向け継続的デプロイ
  (コミットごとの自動デプロイ)へ移行することがあるが、これはフレームワーク既定ではなく
  チームが個別に判断する事項である。
- 本プロジェクトの `4.x` 系ステージ(deployment-pipeline等)はスコープ上SKIPされており、
  実際のデプロイパイプライン設計は本ステージの対象外であるが、方針としての既定値は
  ここに記録しておく。

## Code Style

- フォーマッタ・リンタはプロジェクトルートの設定(`.prettierrc`、`pyproject.toml` 等)に従う。
  言語ごとの標準ツール(Prettier、Black、`gofmt` 等)をCIでマージ前に実行し、失敗した場合は
  PRをブロックする。
- 命名規約は言語の慣用に従う(JS/TSはcamelCase、Pythonはsnake_case等)。チームが明示的に
  合意しない限り、プロジェクト全体を横断するリネームルールは設けない。
- フレームワークがコードスタイルを提案する場合、まずプロジェクトのリンタ設定を確認し、
  リンタで既にカバーされていない場合にのみ提案を適用する。
- 上記に加え、`project.md` に既に確定しているプロジェクト固有規約
  (Apache License 2.0 標準ヘッダーの付与、`reference/` ディレクトリの扱い、
  ドキュメント内のパス表記など)は継続して適用する。技術スタック(言語・フレームワーク)
  自体は本ステージ以前に確定していないため、具体的なフォーマッタ/リンタの選定は
  技術選定が固まった段階で明確化する。

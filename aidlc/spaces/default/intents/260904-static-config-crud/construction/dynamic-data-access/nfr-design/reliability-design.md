# Reliability Design: dynamic-data-access

自宅サーバ1台構成のため、SLA/SLO数値目標は設けない。

## 後勝ち更新(競合制御なし)

動的クエリ実行コンポーネントは、対象RDBMSのバージョン列・最終更新日時列を前提とした競合検出を行わず、PUT時点の主キー一致のみでUPDATE文を実行する(BR3.3、NFR-CONSISTENCY.1)。単一利用者中心・自宅サーバ1台という想定運用規模を前提とした明示的な簡素化のトレードオフである。

## 外部キー制約違反の扱い

新規作成・更新時の外部キー制約違反は、動的クエリ実行コンポーネントがDB側の制約エラーを検出し、サービスコンポーネントが400として応答する(BR3.4、NFR-CONSISTENCY.2)。アプリケーション側での事前検証は行わず対象RDBMSの制約に委ねる。

## permission呼び出し失敗時の扱い

サービスコンポーネントが行うpermission Unitへの契約#3プロセス内呼び出しには、明示的な「拒否」判定のケースと、呼び出し自体が失敗するケースの2種類がある。

1. **明示的な拒否判定**: X-Active-Roleがアクセストークンのrolesクレームに含まれない場合、またはテーブル単位の該当アクション権限がない場合(BR4.1)は403を返す。これはpermission自身が正常に応答した結果としての拒否であり、契約#3のFailure behaviorが規定する範囲である。
2. **呼び出し自体の失敗(内部H2接続断等)**: permission自身の内部例外・応答不能は、契約#3のFailure behaviorが規定する範囲外であり、契約summary.mdの共通規約(HTTPステータス割り当て、500=予期しないエラー)に従い500として応答する設計とする。この場合もfail-closed(拒否側に倒す)であり、誤って許可判定に倒れることはない。permission呼び出し自体を握りつぶして許可扱いにするフォールバックは行わない。

## リトライ・サーキットブレーカー

リトライは行わない。permission・config-managementへの呼び出しはいずれも1回のみとし、失敗時は即座にエラーを返す。

## ヘルスチェック

Spring Boot Actuatorの標準`/actuator/health`エンドポイントに委ねる。

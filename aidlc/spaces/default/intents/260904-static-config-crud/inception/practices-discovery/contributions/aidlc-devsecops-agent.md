## Contribution
開発者一人の趣味プロジェクトであるため、エンタープライズ向けの重厚なセキュリティ体制(専任SOC、DAST、ペネトレーションテスト外部委託等)は過剰であり提案しない。現実的な水準として、バックエンド(Java/Spring Boot/Gradle)は静的解析にSpotBugs/PMDまたはCheckstyleのセキュリティルールセット、依存性の脆弱性検知にはGradleの`dependencyCheck`プラグイン(OWASP Dependency-Check)またはGitHub Dependabotのアラート機能を、CIパイプライン確定時に無料枠で組み込むことを推奨する。フロントエンド(React/TSX)はESLintのセキュリティ系プラグイン(eslint-plugin-security相当)と`npm audit`の実行で足りる。これらはいずれもCI Pipelineステージで具体的なツール選定を行う際の出発点であり、失敗時にビルドを止めるかは開発者自身が採否を決めればよい。

内部H2データベースの接続情報・パスワードハッシュのソルトやペッパー、アクセストークンの署名鍵(HMACの秘密鍵、またはRSA/EC鍵ペア)は、いずれもソースコード・Gitリポジトリに一切コミットしないことを必須とする。自宅サーバでの単一インスタンス運用という前提を踏まえ、エンタープライズ的なシークレット管理サービス(Vault等)の導入は過剰であり、環境変数または実行ユーザーのみが読めるパーミッション(600)を設定したローカルの設定ファイル(Gitの追跡対象外・`.gitignore`登録)で足りると判断する。H2のファイルベース永続化を採用する場合、DBファイル自体にもOSレベルのファイルパーミッションで実行ユーザー以外のアクセスを制限すべきである。トークン署名鍵はサービス起動時に生成/ローテーションする運用か、固定鍵を上記と同様の方法で保管するかを、ドメイン設計以降で具体化してほしい。

make-you-chic-ui と java-mustache-processor はいずれも開発者自身が作成したプロトタイプ段階の自作ライブラリであり、Maven Central/npmに未公開という点はサプライチェーン上のリスクではなく、むしろ第三者パッケージレジストリ経由の依存(タイポスクワッティング等)を回避できている点で有利である。ただし取り込み方式(gitサブモジュール、ローカルパッケージ、モノレポ内配置等)によっては、ビルド時にバージョン固定(コミットハッシュ指定等)を怠ると意図しない変更が本体ビルドに混入するおそれがあるため、取り込み方式の具体化時(ドメイン設計以降)に「参照するバージョン(コミットハッシュ/タグ)を明示的に固定する」ことを条件として付け加えることを推奨する。両ライブラリとも開発者自身の管理下にあるため、依存性スキャンの対象を通常のサードパーティ依存と同列に扱う必要は薄いが、将来的に外部公開・多者共同利用する場合は改めて評価が必要になる。

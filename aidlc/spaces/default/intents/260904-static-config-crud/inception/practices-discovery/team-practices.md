> `aidlc/spaces/default/memory/team.md` の5セクションへ昇格する内容を、
> チームの言葉でまとめている。

## Way of Working

- **ブランチ戦略**: org.md のデフォルトである**トランク・ベース開発**を踏襲する。
  すべての作業は短命なフィーチャーブランチ経由で `main` にマージする(目安1〜2日)。
  長命ブランチはマージ債務を蓄積するため避ける。
- Construction のworktreeにおけるベースブランチは `main`、マージ先も `main`。
- **squash-merge**: Boltブランチは `main` へsquash-mergeする。1 Bolt = 1コミットとし、
  Boltの中間コミット履歴はworktreeが破棄されるまでソースブランチ上に残す。
- 開発者が一人(`constraint-register.md` OC-01)であるため、レビュー担当者を分ける
  プルリクエストレビューは前提としない。ただし短命フィーチャーブランチ運用そのものは、
  変更の粒度を小さく保ち、後から履歴を追いやすくする効果があるため維持する。

## Walking Skeleton

- org.md のデフォルトどおり、有効なスコープファイルが `skeleton: on` を宣言する場合のみ、
  Walking Skeleton Boltを最初に実行する。Bolt 1は単独実行・ゲート付きとし、
  残りのBoltを続けるかどうかはユーザーが明示的に承認する。
- `skeleton: off` の場合はスケルトン儀式を省略し、最初のBoltも通常のBoltと同様に扱う。
- **本プロジェクトでの決定**: MasterSmithは「業務DBのスキーマ読み込み → 内部H2への
  設定保存 → 動的画面生成」という複数レイヤーを貫通する骨格が成立するかどうかが
  アーキテクチャ上の最大の不確実性であるため、`skeleton: on` を採用する。
  Bolt 1では、業務DBスキーマ読み込み→内部H2設定保存→動的画面生成という一連の流れを
  一通り貫通させる薄いバージョンを作る。

## Testing Posture

- **Methodology**: custom
- **Ordering**: 基本は「まず実装し、その後にそのレイヤーのテストを書く」(test-after)
  の順序とするが、スキーマ読み込み層(JDBC `DatabaseMetaData` によるPostgreSQL/MySQL/
  MariaDBの3種読み込み)に限っては、実装に先立ってRDBMSごとの期待挙動(複合主キーの
  構成、主キーなしテーブルの扱い、ビューの読み取り専用扱い)を特性テスト
  (characterization test)として洗い出してから実装を固める、前倒しの順序を採用する。
- 上記の前倒し運用は品質担当の提案どおりに採用したものであり、テスト後書きの原則自体は
  他のレイヤー(内部設定管理、REST API、React/TSXコンポーネント)には変更なく適用する。
- 適用されるスコープ(mvp/feature等)に応じたカバレッジ床(80%ラインカバレッジ+CI実行)は、
  スコープ定義ステージで確定するスコープに従う。スキーマ読み込み層については、カバレッジ
  数値の達成そのものよりも、raid-log.mdで特定済みのリスク(複合主キー、主キーなしテーブル、
  ビュー、RDBMS間の型差異)が個別のテストケースとして明示的にカバーされているかを優先する。
- CI/CDプラットフォームそのものは未決定であり、テストの自動実行ゲート(push/PR時のlint+
  単体テスト実行、失敗時のマージブロック)の具体的な組み込み方は、Construction段階の
  CI Pipelineステージで確定する。

## Deployment

- ステージング/本番の2段階分離は行わない。実行環境は自宅サーバ1台のみであることを前提に、
  **タグを打って手動でデプロイする**シンプルな運用を採用する。
- CI/CDプラットフォームの具体的選定(GitHub Actions等)は、Construction フェーズの
  CI Pipeline / Deployment Pipeline ステージで確定する。

## Code Style

- org.mdのデフォルト方針(プロジェクトレベルのフォーマッタ・リンタ設定を優先し、
  フレームワークの提案はリンタでカバーされない場合のみ適用)を踏襲する。
- **バックエンド(Java 25 / Spring Boot / Gradle)**: フォーマッタ・リンタの具体的な
  ツール選定(Spotless、Checkstyle等)は今は決めず、Construction段階のCI Pipeline
  ステージで確定する。
- **フロントエンド(React/TSX)**: Prettier(フォーマッタ)+ ESLint(リンタ)を
  JS/TSプロジェクトの言語デフォルトとして採用する。既存の自作デザインシステム
  `make-you-chic-ui` のコーディング規約があれば、それに合わせる。
- **内部H2データストアの命名規約**: 内部H2データストアのテーブル・カラム名には専用の
  接頭辞(`ms_` 等)を付ける。これにより、設定値として格納される業務DB由来の
  識別子文字列(テーブル名・カラム名の文字列そのもの)と、MasterSmith自身の
  スキーマオブジェクト名を、コード上・ログ上で混同しないようにする。
- 命名規則は言語慣用(Java: camelCase、TSX: camelCase/PascalCase)に従い、
  プロジェクト独自のリネームルールは現時点で提案しない。
- 未公開の自作ライブラリ2件(`make-you-chic-ui`、`java-mustache-processor`)の
  具体的な取り込み方式(gitサブモジュール等)や、参照バージョン固定の方針は、
  今は決めず、ドメイン設計以降で扱う。

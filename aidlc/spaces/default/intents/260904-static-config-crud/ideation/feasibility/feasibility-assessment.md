# Feasibility & Constraint Assessment: MasterSmith

## Overview

`intent-statement.md` で確定した方向性(静的設定駆動のCRUD管理画面生成、権限定義+簡易ログインを含むMVP)を、技術的に実現可能かという観点で検証した。検証はテスト用スキーマ(家電ECサイト・ポイント管理・蔵書管理という3つの異なる業務ドメインのダミースキーマ+ダミーデータ)を用いて行う想定である [Q1]。

## Technical Viability

### スキーマ読み込み(JDBC DatabaseMetaData)

- 対象RDBMSはPostgreSQL/MySQL/MariaDB(MasterMeisterと同様)[Q9(intent-capture)]。JDBCドライバはアプリケーションに内包する。
- 複合(複数カラム)主キーのテーブルも対象とする。主キーのないテーブルはUPDATE/DELETE対象外(表示・検索は可)とし、スコープを限定することでリスクを抑える。ビューは表示専用でサポートし、更新は行わない。ストアドプロシージャは対象外とする [Q5]。
- MasterMeisterのスキーマ読み込みコードは再利用せず、新規に書き起こす方針 [Q3]。設計思想(静的設定駆動)が異なるため、素材としての参考にとどめる。

### アプリケーション構成

- バックエンド: Java 25 / Spring Boot / Gradle によるステートレスなREST API [Q2][Q7]。
- フロントエンド: React(TSX)によるSPA。自作デザインシステム make-you-chic-ui を活用する [Q11]。必要なフォーム部品(TextInput/Textarea/Select/Checkbox/Switch/RadioGroup)・Table部品・List View/Detail Viewの参考実装・4軸テーマ機能(ライト/ダーク、ブランドカラー、フォント、文字サイズ)を確認済み。同リポジトリはプロトタイプ段階でnpm未公開のため、取り込み方式(gitサブモジュール等)は後続フェーズ(ドメイン設計)で具体化する **[assumption]**。
- 認証: ステートレスなアクセストークン方式(セッションではない)[Q7][Q12]。
- ビルド・パッケージング: フロントエンド/バックエンドは別々に開発するが、単一の実行可能WARにパッケージングする。フロントエンドのビルド成果物はバックエンドの静的コンテンツとして取り込む [Q12]。
- 開発時はフロントエンド(Vite)のdevサーバのproxy設定でバックエンドAPIへ転送する。実行時は単一WARがSPA配信とAPI提供を兼ね、同一オリジンとなるためCORS対応は不要。SPAのクライアントサイドルーティングに対応するため、該当しないパスは `/index.html` へフォールバックする [Q14]。
- 可観測性: OTel(OpenTelemetry)に設定だけで対応できる構成としておく。ログは構造化ログとする [Q13]。
- アプリケーション構成はTwelve-Factor Appの原則に従う(設定の外部化・ステートレスプロセス等)[Q9]。
- 実行インスタンスは業務ごとに個別に分ける(1インスタンス=1業務)。コード・実行モジュールは共通 [Q4]。
- 実行環境は自宅サーバ [Q9]。

### 内部データストア(H2)

- 接続先の業務DB(PostgreSQL/MySQL/MariaDB)とは別に、MasterSmith自身の内部DBとしてH2を使用する。業務DBに設定・アカウント情報を相乗りさせることは不適切と判断 [Q15]。
- 内部DBには利用者アカウント・権限設定に加えて、設定全体(DB接続先設定・メニュー構成・検索条件・一覧表示項目・編集対象外項目・バリデーション・フォーム部品・論理表示名の9項目すべて)を保持する [Q15]。これにより、当初の要件ドキュメントで未決定だった「設定の保持形式」は設定DB方式(H2)に確定した。
- 「静的設定駆動」という設計思想との両立: 設定はキャッシュを介して扱う。起動時(または初回アクセス時)にDBから読み込みキャッシュし、以降はリクエストのたびにDBを見に行かない。明示的なキャッシュクリア操作、またはキャッシュ設定のexpireによってのみ再読み込みされる [Q16]。これにより、DBに保持しつつも実行時の動的解釈を避けるという方針上の整合性を保てると判断する。
- 設定はDB格納に加え、設定ファイルとしてエクスポート/インポートできるようにし、バックアップ・可搬性を確保する [Q17]。
- H2はローカルファイルシステムへの永続化・サーバモード運用・インメモリ(テスト用)のいずれにも対応できるため採用 [Q15]。

### メール送信

- ログイン機能(Q13)の具体化として、アカウントのライフサイクル管理に伴うメール送信が必要になる: アカウント作成通知(URL経由で氏名・パスワードを設定して登録完了)、アカウント登録完了通知、アカウント情報変更通知(氏名・パスワード・メールアドレス)、パスワード変更通知、パスワード忘れ対応、メールアドレス変更リクエスト(新アドレスへの確認メール、現在パスワードの入力で変更完了)[Q18]。
- メールの文面テンプレートには自作のMustacheエンジン java-mustache-processor を使用する。HTML形式とし、`<title>`要素をメールのSubjectとする [Q18]。同リポジトリもmake-you-chic-uiと同様、Maven Central等未公開のプロトタイプ段階であり、取り込み方式の検討が必要 **[assumption]**。
- これらのメール送信フローは、Q13で確定した「シンプルなログイン機能」の範囲をかなり具体化・拡張するものであり、MVPスコープに全て含めるかどうかは次のScope Definitionステージで確認する必要がある **[assumption]**。

### 権限モデル

- テーブル単位・操作単位で権限を定義できる枠組みをMVPに含める(intent-statement.md Q12)。MasterMeisterの権限モデルを参考にする [Q8]。具体的なモデル(グループ/ロール等)の詳細設計はドメイン設計以降で行う。

## Team & Skill Fit

- 開発者は一人(intent-statement.md Q6)。バックエンド(Java/Spring Boot/Gradle)・フロントエンド(React/TSX)の両方を一人で開発する必要があるが、フロントエンド側は既存のデザインシステム(make-you-chic-ui)という資産があるため、SPA化に伴う追加負荷は軽減されると判断する。

## Risk Analysis

詳細は `raid-log.md` を参照。主要リスクの要点:
- make-you-chic-uiがプロトタイプ段階でnpm未公開であること(取り込み方式の検討が必要)
- 複合主キー・ビューなど、3種類のRDBMS間でのJDBC DatabaseMetaData取得結果の差異
- 設定をDBに保持することと「静的設定駆動」の方針との整合性(キャッシュ機構での対応を予定)

## Overall Verdict

**実現可能(Feasible)** と判断する。個人の趣味プロジェクトとしてリスク許容度が高く、致命的な技術的障壁は見当たらない。ただし、成功指標の定量化(intent-capture stageのレビュー指摘R-01、Unresolvedのまま持ち越し)は、次段階(要求分析)で改めて扱う必要がある **[assumption]**。

## Assumptions & Open Questions

- make-you-chic-uiの取り込み方式(gitサブモジュール/ローカルパッケージ等)は未決定。ドメイン設計以降で具体化する **[assumption]**。
- 内部H2 DBのモード(ファイル永続化/サーバモード)は環境(自宅サーバ/テスト)ごとに使い分ける想定だが、詳細な切り替え方針は未決定 **[assumption]**。
- java-mustache-processorの取り込み方式は未決定。ドメイン設計以降で具体化する **[assumption]**。
- アカウントライフサイクルに伴う一連のメール送信フロー(Q18)をMVPスコープにすべて含めるか、一部を将来拡張とするかは、次のScope Definitionステージで確認する **[assumption]**。
